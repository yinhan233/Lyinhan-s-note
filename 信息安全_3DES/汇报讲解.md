# 3DES 文件加解密：汇报讲解稿

展示项目根目录的 [main.c](../../Study/信息安全/3DES实验/main.c)、[des3.c](../../Study/信息安全/3DES实验/des3.c) 和 [file_crypto.c](../../Study/信息安全/3DES实验/file_crypto.c)。代码保留关键注释，详细说明见 [实现与流程.md](实现与流程.md)。

## 1. 开场和模块划分

> 本实验用 C 实现 DES，再调用三次 DES 组成三密钥 3DES。文件采用 CBC 模式，末尾使用 ANSI X9.23 填充。读写按二进制字节处理，所以可以恢复文本、图片和空文件。

展示 [模块图](diagrams/06_modules.png)：

> 工程按三个主要职责划分。`des3.c` 负责单块算法，`file_crypto.c` 负责文件分组、CBC 和填充，`main.c` 负责命令行与打开关闭文件。短小的辅助函数放在使用它们的模块中，通过 `static` 保持内部使用。

## 3. DES 和 3DES 简要讲解

结合 [轮密钥图](diagrams/02_key_schedule.png) 和 [DES 图](diagrams/03_des.png)：

> DES 每次处理 64 位，也就是 8 字节。初始置换后拆成左右两半，每轮新左边等于旧右边，新右边等于旧左边异或轮函数结果。16 轮后交换、最终置换。解密仍用这个结构，只倒序使用轮密钥。

```c
uint32_t next = left ^ des_f(right, key->round[index]);
left = right;
right = next;
```

> `next` 保存新右半部，防止更新变量时丢失旧值。轮函数依次做 E 扩展、异或轮密钥、S 盒和 P 置换。

定位 `triple_block`：

```text
加密：明文 → E(K1) → D(K2) → E(K3) → 密文
解密：密文 → D(K3) → E(K2) → D(K1) → 明文
```

> 3DES 复用三次 DES，密钥总长 24 字节，分组仍为 8 字节。

## 4. 重点：如何处理任意文件

先展示 [CBC 加密图](diagrams/04_encrypt.png)，从 `encrypt_stream` 的头部写入讲起。

> 加密文件前 16 字节是本程序的封装：8 字节标识 `T3CBC001`，再加 8 字节 IV。后面才是密文。解密直接从头部取得 IV，所以命令行不需要再传一次 IV，密钥仍由用户提供。

然后定位 `fread`：

```c
size_t count = fread(block, 1, BLOCK_SIZE, input);
```

> 每次读最多 8 字节，因为元素大小是 1，返回值就是本次字节数。读满时处理完整块，不足时补齐。返回 0 可能是正常结束，也可能出错，所以必须检查 `ferror`。文件中的零字节也是数据，不能用 `strlen` 判断文件内容长度。

接着讲 CBC：

```text
Ci = 3DES加密(Pi XOR 前一密文)
Pi = 3DES解密(Ci) XOR 前一密文
第一块的“前一密文”使用 IV
```

> 加密先异或再加密，解密先解密再异或。`previous` 保存前一密文；解密时必须先保留当前原始密文，供下一轮使用。

### 末块填充

> `ABC` 为 3 字节，填充后是 `41 42 43 00 00 00 00 05`。最后的 `05` 说明补了 5 字节。如果文件长度本来是 8 的倍数，也额外加 `00 00 00 00 00 00 00 08` 一整块。空文件同样补这一块。

> 这样每个密文块都完整，而且解密可以明确知道最后删多少字节，原文末尾的零不会被误删。

### 预读识别最后一块

结合 [CBC 解密图](diagrams/05_decrypt.png)：

> 解密不知道当前块是否为最后一块，因此预读下一块。如果还能读满 8 字节，当前块写回完整明文；如果读到 0 且没有错误，当前块才去填充；如果读到 1～7 字节，说明密文长度不合法。缓冲区只保存当前和下一块，不需要把整个文件读进内存。

### 打开、关闭和失败清理

定位 `main.c` 中的 `fopen` 和 `fclose`：

> 输入用 `rb` 读取原始字节，输出用 `wbx` 独占新建，防止覆盖已有文件。每次读写都检查结果；写入可能先进入标准库缓冲区，所以还要检查 `fclose`。只有处理和关闭都成功才报告完成，出错时尝试删除本次不完整输出。

## 5. 现场演示

在项目目录执行：

```bash
make

DEMO_DIR=$(mktemp -d ./report-demo.XXXXXX)
KEY=0123456789abcdeffedcba987654321089abcdef01234567
IV=1234567890abcdef

printf 'ABC' > "$DEMO_DIR/原文.txt"
./build/des3 enc "$DEMO_DIR/原文.txt" "$DEMO_DIR/密文.bin" "$KEY" "$IV"
./build/des3 dec "$DEMO_DIR/密文.bin" "$DEMO_DIR/恢复.txt" "$KEY"
xxd "$DEMO_DIR/密文.bin"
cmp "$DEMO_DIR/原文.txt" "$DEMO_DIR/恢复.txt"
sha256sum "$DEMO_DIR/原文.txt" "$DEMO_DIR/恢复.txt"

# 用图片验证文件类型不影响处理；省略 IV 时随机生成。
./build/des3 enc ../实验要求.png "$DEMO_DIR/图片密文.bin" "$KEY"
./build/des3 dec "$DEMO_DIR/图片密文.bin" "$DEMO_DIR/恢复图片.png" "$KEY"
cmp ../实验要求.png "$DEMO_DIR/恢复图片.png"

```

解释 `xxd`：前 8 字节为标识，接着 8 字节为 IV，最后 8 字节为密文。3 字节原文的加密文件因此是 24 字节。没有 `xxd` 可用 `od -An -tx1`。

`cmp` 无输出且返回 0 代表逐字节相同。SHA-256 用来直观展示两个文件一致；算法正确性还要结合已知向量和 OpenSSL 独立对照。

## 6. 常见问题

**为什么三个密钥仍只处理 8 字节？**

三次 DES 处理的是同一个分组，每次长度都不变；24 字节是三段密钥的总长度。

**为什么采用 EDE？**

这是本实验使用的 3DES 结构。三个密钥相同时，中间加解密可以抵消，整体与一次 DES 相同。

**为什么空文件不是只有头部？**

空文件也补一个分组。解密去掉 8 字节填充后写出 0 字节，恢复为空文件。

**为什么不只补零？**

原文件本来可能以零结尾。最后一字节记录长度，才能区分原文和填充。

**为什么要预读，不能解完一块就立即去填充？**

只有最后一块含填充，中间块的末字节可能恰好也是 1～8。预读用于识别真正的末块。

**为什么只加密再解密还不足以证明正确？**

两端可能犯同一种错误却仍互相恢复。因此额外检查 DES、3DES 已知向量，并与 OpenSSL 比较密文主体。

**错误密钥一定能检测吗？**

不能。填充校验只能发现部分错误，文件没有认证标签，成功解密不构成未被修改的证明。

**为什么还保留两个头文件？**

它们声明算法和文件流接口，源文件分别编译再链接。入口不需要自己的头文件，短小的私有辅助函数也无需各自拆出一个模块。
